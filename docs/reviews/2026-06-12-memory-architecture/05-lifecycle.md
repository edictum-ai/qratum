# Review 5: Lifecycle and Missing Pieces

- Lens: the design describes how memories get IN — attack everything after, around, and instead
- Model: Fable (relaunch; the killed Opus run's partial findings were independently re-derived)
- Date: 2026-06-12

Evidence base: read gateway code (`src/domain/access.ts`, `content-policy.ts`, `src/application/use-cases/persistent-memory.ts`, `src/infrastructure/tidb/memory-repository.ts`, `migrations/tidb/*.sql`, `src/interfaces/mcp/phase0-server.ts`, `memory-guidance.ts`, `docs/roadmap.md`, `docs/contracts.md`) and Qratum specs (`specs/current/operational-model-redesign.md`, `specs/current/memory-curation-pipeline.md`, milestone-a). No importer code exists anywhere in the personal-memory repo (grep: only a roadmap mention) — the importer is contract-only. No lesson code exists in Qratum (`internal/`, `cmd/` grep empty).

## F1 — The system has NO mutation verb, end to end — VERIFIED GAP, BLOCKER

- Gateway tools in code: `memory_search` and `memory_store` only — `src/domain/access.ts:11` (`MemoryToolName = "memory_search" | "memory_store"`). `memory_update`/`memory_delete` are roadmap items (`docs/roadmap.md:84,182`; `docs/contracts.md:109-114`). **Nothing in `src/` ever sets `deleted_at`** — the column exists (`migrations/tidb/001:16`), is filtered in every query, and has zero setters. Today the only correction path in the entire two-repo system is hand-written SQL against production TiDB.
- Qratum lesson lifecycle is terminal at `exported`: `suggested -> staged -> approved -> exported`, `any non-exported -> rejected` (`memory-curation-pipeline.md:214-219`). Edits are allowed only *before* approval (`:246-248`). Operational lifecycle is strictly forward (`operational-model-redesign.md:249-305`); `publish revoke` is explicitly deferred and "cannot guarantee recall from external destinations" (`:985-987`). Even *local* edit-after-export has no defined semantics — re-export of an edited lesson produces a new content hash -> a NEW gateway row; the stale sibling stays live and ranks identically.
- Concrete 6-month scenario, with built-in irony: the Tier-0 payload is a snapshot of claude.ai's auto-accumulated memory — exactly the kind of corpus that contains stale framings like the `edictum-console` product shape that the user's own CLAUDE.md files explicitly fight. Qratum will faithfully atomize, approve, and deliver that stale framing into the store **every agent reads at runtime**, and no tool, UI, or transition anywhere can correct it. The pipeline doesn't just fail to handle staleness — it starts by importing pre-stale content.
- **Fix shape:** (a) Gateway: ship soft `memory_delete` first (already roadmap "planned" — promote it ahead of everything in the Curation Track; it is the prerequisite for every other lifecycle feature). Add optional `supersedes: [id]` to `memory_store` that soft-retires listed rows transactionally — append-mostly, auditable, tiny. (b) Qratum: add `exported -> superseded_by(les_X)` and `exported -> retracted` transitions plus a `memory_retraction` item type in bundles. For one person this is days of work, and it is the difference between a knowledge base and a landfill.

## F2 — Receipts don't capture the gateway memory ID — VERIFIED GAP, SERIOUS

The importer receipt records `lesson_id, content_sha256, outcome` (`memory-curation-pipeline.md:383-388`). The gateway's store response *does* return `memoryIds` (`persistent-memory.ts:93`) — the receipt contract just doesn't keep it. Consequence: Qratum can never address a gateway row except by natural key `(namespace, subject, content_hash)` — and the gateway roadmap **already plans to mutate that key** via the namespace reclassification pass (`roadmap.md:80-82`: "existing personal rows need a reclassification pass"). The day that migration runs, every Qratum `exported` marker dangles and any future retire/supersede flow is blind. One-line contract fix now (record `memory_ids` per receipt line); archaeology later.

## F3 — Delete/upsert collision and resurrection — VERIFIED GAP, SERIOUS

`memory-repository.ts:15-25`: `ON DUPLICATE KEY UPDATE ... deleted_at = NULL` on unique key `uk_memory_records_dedupe (namespace, subject, content_hash)` (`migrations/tidb/002:23`). Walked scenarios:

- **Receipt loss -> resurrection.** Same-bundle re-run is safe only while `import_receipt.jsonl` — a loose file next to a bundle in a local folder — survives. Lost receipt (cleanup, laptop restore, second machine) -> re-run -> byte-identical store -> intentionally deleted row silently resurrects. The design says Qratum "ingests" the receipt into lesson status, but lesson status (`exported`) doesn't prevent the *importer* from re-running; the receipt file is the only guard, and it's the most fragile artifact in the system.
- **Any byte-identical writer resurrects.** Once `memory_delete` ships, an agent that previously *read* a memory and later re-stores it verbatim (agents do this) undeletes it. The roadmap documents this as a semantic, not a bug (`roadmap.md:87-88`) — it's a bug.
- **Provenance is destructible by any writer.** The upsert overwrites `source_client` and `metadata` wholesale (`memory-repository.ts:16-23`). An agent storing content byte-identical to a Qratum-curated row silently replaces Qratum's provenance (lesson_id, bundle_id, source_digest) with `clientName: claude-code`. Last-writer-wins on the audit trail of a security-conscious system.
- **Fix shape:** `memory_store` must return a discriminator (`created | updated | resurrected`); resurrect must be explicit (reject duplicate-of-deleted with a distinct errorClass, require explicit restore); upsert should merge, not replace, provenance metadata; Qratum should ingest receipt *files* into the vault as objects, not leave them beside bundles.

Corollary VERIFIED contract bug, annoyance: the importer contract promises a `duplicate` outcome (`memory-curation-pipeline.md:385`) that the gateway response cannot produce — insert and dedupe-update return identical shapes (`persistent-memory.ts:84-98`).

## F4 — Namespace slug mismatch can strand the entire Tier-0 payload — VERIFIED GAP, SERIOUS

`memory_search` is strictly single-namespace — `namespace = ?` in both SQL paths (`memory-repository.ts:71-96`), schema defaults to `"personal"` (`phase0-server.ts:35`). No cross-namespace search, no namespace enumeration tool, no way for an agent to discover which `project:<slug>` namespaces exist. Qratum maps project scope to `project:<slugified claude.ai project name>` (`memory-curation-pipeline.md:147-149,344-349`) — but claude.ai project names ("AI Contracts" -> `ai-contracts`) are not repo slugs (`project:qratum`), which is what runtime agents will plausibly guess. Nothing in either repo defines a canonical slug registry; the gateway roadmap itself flags repo-local namespace config as undesigned (`roadmap.md:61-63`). **Net effect: the carefully curated memories land in 13 namespaces that no runtime agent ever searches, and the search tool defaults everyone into `personal`.** The import produces rows, not retrievable memories. Fix: collapse to far fewer namespaces at export (e.g., everything -> `personal`/`coding` until per-repo namespace config exists), or ship the repo-local namespace config first. For ~30-60 memories, 13 project namespaces is fragmentation with zero upside.

## F5 — Retrieval ignores everything the pipeline curates — VERIFIED GAP, SERIOUS (compound)

- Ranking is raw cosine, no distance threshold, no recency weighting (`memory-repository.ts:71-82`): top-K always fills with *something*, however irrelevant, in small namespaces.
- `contentClass` is stored but never filtered, never ranked, and **not returned in search results** (`persistent-memory.ts:132-138` returns only id/namespace/source/updatedAt/content). Qratum's spec invests real ceremony in kind-mapping ("the gateway silently coerces unknown classes to note, which would destroy classification — Qratum must never rely on that fallback", `memory-curation-pipeline.md:352-356`) **to protect a field nothing reads.** Same for the provenance metadata: nested under `metadata.clientMetadata`, unsearchable, unreturned — write-only.
- Atomization risk: Tier-0 splits on markdown structure (`:139-152`) with no rule that candidates carry their heading path — a bullet under "Things to avoid" becomes a free-floating assertion with inverted polarity. Mitigated by human review of ~30-60 items, but the default extraction loses meaning; add "candidates carry heading-path prefix" to the parse rules.
- **Embedding-model pinning time bomb:** every query filters rows to the *current* provider/model/dimensions triple (`memory-repository.ts:60-82`; provider is an env var, `config.ts:62`). Change `MEMORY_EMBEDDING_PROVIDER` or bump the Titan model and the entire store becomes invisible to search — not deleted, invisible, silently. No re-embedding job exists anywhere. This is orthogonal to Qratum but lethal to "curated knowledge home". Fix: a re-embed backfill script plus a startup warning when rows exist under a non-current embedding triple (the `countSql` data is already there).

## F6 — Two write paths: the firehose is ungoverned, the trickle has the ceremony — VERIFIED GAP, SERIOUS

The gateway's own server instructions tell every agent to "store... after work" (`memory-guidance.ts:3-12`). Dedup is exact-hash only (`persistent-memory.ts:78`); semantically identical facts in different words always create separate rows. The design deleted `staging:<target>` for the Qratum lane and reassigned live-store hygiene to a personal-memory-side job — whose status in the roadmap is "approved as next product theme, **design not started**" (`roadmap.md:25-31`). So: the curated path (one-time ~30-60 items plus occasional lessons) gets approval, consent, pre-flight, receipts; the uncurated path (every agent, every day, forever) gets nothing, and they converge on the same namespaces, same subject, indistinguishable except `source_client`. Timeframe: with daily Claude Code + Codex + web agents at maybe 5-30 writes/week, common topics will have several near-duplicate variants within 2-3 months; with a 5-result default search limit, redundant variants crowd out diverse results well before month 6 — and there is no delete tool to clean any of it (F1).

Right shape for one person: not staging namespaces, and not a batch consolidation daemon — a **write-time near-dup check in the gateway**. The store path already computes the embedding (`persistent-memory.ts:72`); one nearest-neighbor query before insert, and within-threshold writes become `updated_at` refreshes (a salience signal the roadmap already wants, `roadmap.md:132-134`) instead of new rows. ~50 lines in `storeMemory`, kills the dominant degradation mode at the source.

Note also doc drift: `staging:<target>` is still in the roadmap on disk (`roadmap.md:49-50`), and both Qratum specs still reference the supposedly-deleted SQLite LessonBackend (`memory-curation-pipeline.md:291-292`, `operational-model-redesign.md:1536-1541`). The decisions in this architecture exist in nobody's repo — annoyance, but for a spec-driven factory that's how decisions get silently un-made.

## F7 — No per-namespace grants: `private` is readable/writable by every connected agent — VERIFIED GAP, SERIOUS

`authorizeTool` checks only scope + allowlist membership (`access.ts:55-80`). Any identity with `memory:read` — including ChatGPT web — can `memory_search(namespace="private")`. A prompt-injected web agent exfiltrating the `private` namespace is a one-call attack. The roadmap knows ("namespace naming is not enough; enforce per-client grants server-side", `roadmap.md:51-52`) but it's in "Next". By this user's own security bar (least-privilege, approval boundaries — it's literally the Edictum pitch), shipping more curated content into this store *raises* the value of that gap. Minimum fix before Tier-0 import: a static client->namespace grant map in config; it's a 30-line check in `authorizeTool`.

## F8 — Feedback loop — SUSPECTED GAP, ANNOYANCE (mostly premature), with one cheap exception

Retrieval signal already exists and is unread: every `memory_search` audit event records returned `memoryIds` (`phase0-server.ts:51,131-155`; `memory_audit_events`). "Never retrieved in N months" is a derivable retire signal needing zero new instrumentation — the future hygiene job should be specced to read it. Building useful/harmful feedback tooling for one user now is premature. The non-premature piece is F1 again: the human *is* the feedback loop, and the human has no verb — when an agent surfaces a wrong memory mid-session, there is nothing the user can do at the point of encounter.

## F9 — The other 99%: priority inversion in the export lane — SUSPECTED GAP, SERIOUS (founder time)

ATTACKED-AND-HELD in part: vault+refinery is *not* justified by the export — it's justified by claude-code live capture, which Milestone A already built. The export rides existing rails. **But** the P2 adapter mandates normalization of all 556 conversations / 11,962 messages / 187MB (`memory-curation-pipeline.md:108-125`) whose only consumer is Tier 2 — consent-gated, cost-gated, deferred, plausibly never shipped. Meanwhile Tier 1 — the 447 ready-made summaries, the obvious cheap intermediate, already redaction-safe and short — is "deferred decision; optional" (`:154-159`). The spec defers the cheap middle while building plumbing for the expensive end. Fix: Tier 0 needs only `memories.json`; archive `conversations.json` as a content-addressed blob (archive != normalize), promote Tier 1 into the vertical slice, and gate per-conversation Session/Revision normalization on an actual Tier-2 consent decision.

## F10 — Durability and multi-machine — SUSPECTED GAP, SERIOUS for the vault, acknowledged for the cloud

Gateway side: ATTACKED-AND-HELD — EBS snapshots with logical backup consciously deprioritized, documented with the risk owner named (`roadmap.md:188-197`). Qratum side: no backup story exists anywhere in the specs (grep across SPEC.md, operational model, ADR-0007: only a "backup manifest" for migrations). Laptop dies -> curated memories survive in cloud, but you irrecoverably lose: the raw archive ("retention: forever" — forever on one disk), lesson objects and statuses, the rejected-lesson set (whose entire purpose is preventing resurfacing on re-extraction), receipts (F3), consent records, tombstones. Also: the roadmap itself places Hermes on a Mac mini — agents demonstrably run on >=2 machines, and capture exists on one. "Local-first" is currently spelled "single-machine". Minimum: a `qrt backup` (restic/rclone wrapper) over the workspace, and an explicit statement that non-laptop sessions are out of scope.

## F11 — Ductum scale vs. the approval queue — SUSPECTED GAP, SERIOUS

The factory is already merging dogfood-capture runs into Qratum (git log: `Merge ductum/P1-REAL-CLAUDE-DOGFOOD-CAPTURE`). At P4, every factory session emits AI lesson candidates; the design's per-lesson human review + per-bundle approval is sized for the one-time Tier-0 batch. At factory volume the staging queue either backs up (pipeline silently dead) or gets rubber-stamped (curation theater). The operational model already hints at the answer ("auto-save low-risk suggestions", `operational-model-redesign.md:1338-1340`) but the curation pipeline doesn't import it. Fix: per-kind/per-confidence auto-approval policy plus batch review UX, designed in *now*, before P4 makes it urgent.

Ecosystem pattern worth naming, not forcing: the gateway is an approval/audit boundary on a side-effecting agent action — what agents may persist — which is precisely the Edictum wedge shape. No integration needed today, but F7's per-namespace grants are the same product idea; building them as if Edictum didn't exist is mild self-blindness, and possibly a future dogfood demo.

## ATTACKED-AND-HELD (probed, genuinely covered)

- **Pull-based bundle handoff, no gateway creds in Qratum** — clean trust boundary in intent, held (other reviewers dispute the mechanism; see reports 1, 3, 6, 7).
- **Pre-flight policy mirror with blocked-never-dropped + receipt for residual rejects** — held (and honest about medical/legal/financial blocking). One mismatch: contracts promise "explicit user confirmation" for high-sensitivity content (`contracts.md:305-306`) but code is an unconditional deny with no confirmation input (`content-policy.ts:49-51`) — and the secret regex will false-positive on legitimate coding lessons *about* secret handling.
- **Same-bundle re-run idempotency** — held, conditional on receipt durability (F3).
- **Rejected-lessons-stay-on-file anti-resurface dedup** — held (but see report 6 on transform-version bumps).
- **Raw-never-leaves boundary** — held consistently across both repos.

## THE ODD SHAPE

**This is a batch ETL architecture bolted onto a stewardship problem, and everything after "deliver" is missing because the design's mental model ends at delivery.** All the big findings — no update/supersede (F1), receipts without IDs (F2), delete/resurrect collision (F3), hygiene assigned to a nonexistent job (F6), no feedback (F8) — are one hole seen from five angles: the forward-only refinery lifecycle, which is *correct* for the one-time export import, got generalized into the permanent architecture, while the live store all agents read daily — the only state that actually determines runtime quality — has no owner, no verbs, and the least design. Stated as one sentence: **Qratum is the system of record for where memories came from; nothing is the system of record for what memories are *now*.** "One home per data class" reads clean but quietly papers over the fact that curated knowledge lives in two stateful homes (lesson objects, gateway rows) connected by a single one-way paper airplane — bundle out, receipt back, once — with no reconciliation verb in either direction. The fix isn't a sync engine; for one founder it's three small verbs (delete, supersede, re-embed) and one ID written into a receipt. But until the design admits the store is alive, every pipeline improvement just delivers freight more reliably to a warehouse nobody can rearrange.
